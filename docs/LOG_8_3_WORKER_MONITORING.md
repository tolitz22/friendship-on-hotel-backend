# LOG-8.3 — Worker and scheduler monitoring

Deploy the backend migration first: php artisan migrate --force. The new platform_heartbeats table contains at most four application-managed rows, one each for scheduler, queue_worker, push_started and push_completed. Updates replace existing rows, not append history. The database must be shared between API and worker. Existing schedule:work start command stays unchanged. A scheduled heartbeat runs every minute, including when push is disabled. Queue worker loop/attempt events record at most once per minute per process. Push start/completion record actual command invocations, including manual runs and disabled/failed outcomes. Heartbeats are aggregate last observations, not per-replica liveness or proof of continuous availability. Older than 180s is stale; never seen and unknown are distinct. Long jobs or scheduler delays can make a healthy process look stale. A failed heartbeat never changes business command exit status. No additional service or required environment variable.

The private GET /api/v1/platform/workers endpoint is restricted to dedicated operators, no-store, six requests/min. It reads push outbox counts across properties: due pending (including rows awaiting recovery), delayed, processing, expired leases, oldest due age, currently retained sent/failed rows updated in last 24 hours. These are not historical lifetime counters or delivery guarantees; pruning/cascades affect counts. No payloads, device endpoints, user or hotel IDs. Laravel queue counts refer to configured API default connection (all queues in that database table); sync is not applicable; database table missing is unavailable; failed job persistence disabled is not configured. No generic queue tables created or queue driver changed. No queue retry, prune, recovery or job dispatch performed by the dashboard. To validate scheduler, leave actual worker running and confirm recent scheduler heartbeat after one minute; a manual push command only proves command activity. Confirm worker uses same DB and migrations, role=worker, and restart on new revision. CI uses synthetic data only.
